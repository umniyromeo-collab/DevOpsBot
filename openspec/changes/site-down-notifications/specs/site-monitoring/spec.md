# Spec Delta

## Purpose

Периодическая проверка доступности сайтов из фиксированного списка с частотой, зависящей от недавней
истории сбоев, и определение моментов, когда сайт упал или восстановился.

## ADDED Requirements

### Requirement: Фиксированный список сайтов
Система SHALL при старте загружать из постоянного хранилища список сайтов с базовым интервалом опроса и ожидаемым HTTP-кодом для каждого сайта. Изменения списка во время работы MUST NOT применяться до перезапуска.

#### Scenario: Сайт из списка опрашивается
- **WHEN** чекер запущен и сайт есть в списке
- **THEN** система периодически проверяет этот сайт

#### Scenario: Список изменён после старта
- **WHEN** в хранилище добавлен новый сайт, а чекер уже работает
- **THEN** новый сайт не проверяется до перезапуска чекера

### Requirement: Проверка доступности по сети
Система SHALL проверять HTTP- и HTTPS-сайты реальным сетевым запросом. Проверка считается успешной, только если получен ожидаемый HTTP-код. Отсутствие ответа в пределах таймаута MUST считаться неудачной проверкой.

#### Scenario: Получен ожидаемый код
- **WHEN** сайт ответил ожидаемым HTTP-кодом
- **THEN** проверка считается успешной

#### Scenario: Получен другой код
- **WHEN** сайт ответил кодом, отличным от ожидаемого
- **THEN** проверка считается неудачной

#### Scenario: Ответа нет
- **WHEN** сайт не ответил в пределах таймаута или соединение не установлено
- **THEN** проверка считается неудачной, а HTTP-код равен 0

### Requirement: Базовая частота опроса
Система SHALL опрашивать сайт с его базовым интервалом, если в окне истории у сайта нет неудачных проверок.

#### Scenario: Стабильный сайт
- **WHEN** у сайта нет неудачных проверок в окне истории
- **THEN** интервал между запусками его проверок равен базовому

### Requirement: Учащённый опрос после сбоев
Система SHALL опрашивать сайт чаще базового интервала, если в окне истории есть неудачные проверки. Интервал MUST NOT быть меньше установленной нижней границы и SHALL вернуться к базовому, когда неудачных проверок в окне не останется.

#### Scenario: Недавний сбой
- **WHEN** в окне истории у сайта появилась неудачная проверка
- **THEN** система опрашивает сайт чаще базового интервала

#### Scenario: Нижняя граница
- **WHEN** базовый интервал настолько мал, что расчётный оказался бы меньше нижней границы
- **THEN** система использует нижнюю границу

#### Scenario: Сбои вышли из окна
- **WHEN** в окне истории у сайта не осталось неудачных проверок
- **THEN** система возвращается к базовому интервалу

### Requirement: Одна проверка сайта одновременно
Система MUST NOT запускать новую проверку сайта, пока не завершена предыдущая проверка этого сайта и её результат не передан на запись.

#### Scenario: Предыдущая проверка ещё идёт
- **WHEN** наступил срок проверки, а предыдущая проверка этого сайта не завершена
- **THEN** новая проверка не запускается, и задачи этого сайта не накапливаются

### Requirement: Параллельные проверки
Система SHALL проверять разные сайты параллельно, так что ожидание ответа одного сайта не задерживает проверки других, пока есть свободные рабочие потоки.

#### Scenario: Один сайт отвечает медленно
- **WHEN** проверка одного сайта ждёт ответа, а другому сайту подошёл срок проверки и есть свободный поток
- **THEN** второй сайт проверяется, не дожидаясь первого

### Requirement: Сохранение результатов проверок
Система SHALL сохранять результат каждой проверки: адрес сайта, HTTP-код, доступность и время.

#### Scenario: Результат сохранён
- **WHEN** проверка завершилась, успешно или нет
- **THEN** её результат появляется в постоянном хранилище

### Requirement: Определение падения сайта
Система SHALL считать работающий сайт упавшим после установленного числа неудачных проверок подряд. Успешная проверка MUST сбрасывать счётчик неудач.

#### Scenario: Единичный сбой
- **WHEN** у работающего сайта одна неудачная проверка, а порог равен двум
- **THEN** статус сайта остаётся «работает»

#### Scenario: Порог достигнут
- **WHEN** у работающего сайта две неудачные проверки подряд, а порог равен двум
- **THEN** статус сайта меняется на «упал»

#### Scenario: Сбои вперемешку с успехом
- **WHEN** между двумя неудачными проверками прошла успешная
- **THEN** статус сайта остаётся «работает»

### Requirement: Определение восстановления сайта
Система SHALL считать упавший сайт восстановившимся после первой успешной проверки.

#### Scenario: Сайт снова отвечает
- **WHEN** у сайта со статусом «упал» проверка прошла успешно
- **THEN** статус сайта меняется на «работает»

### Requirement: Начальный статус сайта
Система SHALL считать сайт без сохранённого статуса работающим, так что первая успешная проверка не является сменой статуса.

#### Scenario: Новый сайт работает
- **WHEN** у сайта нет сохранённого статуса и проверка успешна
- **THEN** смена статуса не фиксируется

#### Scenario: Новый сайт сразу недоступен
- **WHEN** у сайта нет сохранённого статуса и проверки неудачны до достижения порога
- **THEN** статус сайта меняется на «упал»

### Requirement: Статус переживает перезапуск
Система SHALL хранить статус сайта и счётчик неудач постоянно и восстанавливать их при старте чекера.

#### Scenario: Сайт лежал до перезапуска
- **WHEN** чекер перезапущен, сайт имел статус «упал» и всё ещё недоступен
- **THEN** статус остаётся «упал», и смена статуса не фиксируется повторно
