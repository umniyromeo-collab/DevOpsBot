# Spec Delta

## Purpose

Доставка подписчикам в Telegram сообщений о падении и восстановлении сайта так, чтобы сообщения
не терялись при падении процессов системы.

## ADDED Requirements

### Requirement: Сообщение о падении сайта
Система SHALL отправлять сообщение о падении каждому пользователю, подписанному на сайт, когда статус сайта меняется на «упал».

#### Scenario: Подписчик получает сообщение
- **WHEN** статус сайта изменился на «упал» и пользователь подписан на этот сайт
- **THEN** пользователь получает сообщение о падении с адресом сайта

#### Scenario: Пользователь не подписан
- **WHEN** статус сайта изменился на «упал» и пользователь не подписан на этот сайт
- **THEN** пользователь не получает сообщения

### Requirement: Сообщение о восстановлении сайта
Система SHALL отправлять сообщение о восстановлении каждому пользователю, подписанному на сайт, когда статус сайта меняется с «упал» на «работает».

#### Scenario: Сайт восстановился
- **WHEN** статус сайта изменился с «упал» на «работает» и пользователь подписан на этот сайт
- **THEN** пользователь получает сообщение о восстановлении с адресом сайта

### Requirement: Сообщения только при смене статуса
Система MUST NOT отправлять сообщения, если статус сайта не изменился.

#### Scenario: Сайт продолжает лежать
- **WHEN** у сайта со статусом «упал» очередная проверка снова неудачна
- **THEN** новых сообщений не появляется

### Requirement: Порядок сообщений по сайту
Система SHALL доставлять сообщения об одном сайте в том порядке, в котором менялся его статус.

#### Scenario: Падение и восстановление
- **WHEN** сайт упал, а затем восстановился
- **THEN** подписчик получает сначала сообщение о падении, затем о восстановлении

### Requirement: Сохранность при падении чекера
Система MUST NOT терять смену статуса при падении чекера. Смена статуса, которая была сохранена, но не передана боту, SHALL быть передана после перезапуска чекера до начала новых проверок.

#### Scenario: Падение между сохранением и передачей
- **WHEN** чекер сохранил смену статуса и упал, не передав её боту
- **THEN** после перезапуска подписчик получает сообщение об этой смене статуса

#### Scenario: Сайт восстановился, пока чекер лежал
- **WHEN** чекер упал, не передав сообщение о падении, а к перезапуску сайт уже работает
- **THEN** подписчик получает сообщение о падении, а затем о восстановлении

### Requirement: Сохранность при падении бота
Система MUST NOT терять сообщения о смене статуса при падении или простое бота. Смена статуса SHALL считаться обработанной ботом только после отправки сообщений всем подписчикам.

#### Scenario: Падение до отправки
- **WHEN** бот получил смену статуса и упал, не отправив сообщения
- **THEN** после перезапуска бот отправляет сообщения подписчикам

#### Scenario: Смена статуса во время простоя
- **WHEN** статус сайта изменился, пока бот не работал
- **THEN** после запуска бот отправляет сообщение подписчикам

### Requirement: Допустимые повторы
Система MAY отправить сообщение о смене статуса повторно, если процесс упал после отправки, но до фиксации этого факта. Повтор MUST NOT искажать порядок смен статуса одного сайта.

#### Scenario: Падение после отправки
- **WHEN** бот отправил сообщение и упал до подтверждения обработки
- **THEN** после перезапуска подписчик может получить то же сообщение ещё раз

### Requirement: Недоступный получатель не блокирует доставку
Система SHALL пропускать получателя, которому отправка отклонена окончательно (например, пользователь заблокировал бота), и MUST продолжать доставку остальным. При временной ошибке Telegram отправка SHALL повторяться.

#### Scenario: Пользователь заблокировал бота
- **WHEN** Telegram окончательно отклоняет отправку одному из подписчиков
- **THEN** остальные подписчики получают сообщение, и обработка следующих смен статуса продолжается

#### Scenario: Временная ошибка Telegram
- **WHEN** Telegram вернул временную ошибку или ограничение частоты
- **THEN** бот повторяет отправку этого сообщения и не считает смену статуса обработанной до успеха
