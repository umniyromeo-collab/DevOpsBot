# Design

## Context

Мотивация — в `proposal.md`, требования — в `specs/`.

Что есть в коде сейчас:

- `ThreadPool` рабочий, но его очередь задач не ограничена; у воркера нет `try/catch`.
- `BoundedThreadSafeQueue` — неработающий черновик, у неё нет способа завершить ожидание.
- `HTTPChecker` покрыт тестами через `net::IFetcher`, но `Fetcher` не собирается: нет конструктора
  и деструктора, файл не входит в цели. `HTTPSChecker` — заглушка.
- `PG::PGStore` — универсальный INSERT со статическим соединением на процесс и транзакцией на запись.
  Заголовок нигде не подключён. Читать он не умеет.
- `telegram::Bot` работает только как long polling; `SendText` приватный, без таймаута и без проверки
  результата.
- Клиента Kafka в системе и в сборке нет. `.env` читать нельзя, настройки приходят из окружения.

## Goals / Non-Goals

**Goals:**

- Сообщения о смене статуса не теряются при падении чекера или бота (at-least-once).
- Логика статуса, очередь и разбор команд проверяются юнит-тестами без сети, БД и брокера.
- Между потоками внутри процесса общая только очередь в чекере и флаг остановки.

**Non-Goals:**

- Несколько экземпляров чекера или бота.
- Переподключение к Postgres и Kafka внутри работающего процесса: при потере соединения процесс
  завершается, а сохранность обеспечивает перезапуск.
- Очистка `check_results` по сроку давности.
- Сборка образа для чекера: `Dockerfile` по-прежнему собирает только `TelegramBot`.
- Удаление `PG::PGStore`, `Storage` и цели `PgDemo`: они остаются как есть и не используются новым кодом.

## Decisions

### Общая схема

```text
checker process (DevOpsBot)                  tgbot process (TelegramBot)
+---------------------------------+          +---------------------------+
| scheduler (main thread)         |          | consumer thread           |
|   |                             |          |   event --> subscribers   |
|   v                             |          |         --> sendMessage   |
| ThreadPool: N workers, Check()  |          |         --> commit offset |
|   |                             |          |                           |
|   v                             |          | poll thread               |
| BoundedThreadSafeQueue          |          |   getUpdates --> commands |
|   |                             |          +------+------------^-------+
|   v                             |                 |            |
| writer thread (exactly 1)       |                 |            |
|   |-- TX --> PostgreSQL <-------+-----------------+            |
|   +-- status != notified? ------+--> Kafka: site-status -------+
+---------------------------------+
```

Чекер определяет смену статуса, потому что только он видит результаты проверок. Бот решает лишь,
кому отправить.

### Соединение с БД — одно на поток

У каждого потока, работающего с БД, свой объект с собственным `pqxx::connection`: в чекере — писатель
и планировщик, в боте — оба потока. Поэтому `pqxx::connection` не разделяется, мьютекс вокруг БД
не нужен, и правило «никакой БД под мьютексом» выполняется само.

Новые классы в `internal/db` реализуют интерфейсы, через которые логика тестируется на фейках:
`PG::CheckerStore` (сайты, состояние, запись результата, история сбоев) и `PG::BotStore` (подписки,
проверка адресов). `DBEntry` не подходит: нужны транзакции из нескольких запросов, UPSERT и чтение.

Альтернативы: общее соединение под мьютексом (БД под блокировкой, нарушает правило 7); кэш подписок
в памяти бота с мьютексом (второй источник правды без выгоды при таком объёме).

### Схема данных

Таблица `check_results` не меняется. Новые таблицы в `db_description.sql`, идемпотентно:

| Таблица | Колонки |
|---|---|
| `sites` | `url` PK, `base_interval_sec`, `expected_http_code` |
| `site_state` | `url` PK → `sites`, `is_up`, `notified_is_up`, `consecutive_failures`, `changed_at` |
| `subscriptions` | `chat_id`, `url` → `sites`, PK (`chat_id`, `url`), индекс по `url` |

При старте чекер создаёт недостающие строки `site_state` со значениями `is_up = notified_is_up = true`.
Так реализуется начальный статус «работает» без отдельного состояния «неизвестно». Содержимое `sites`
заполняется отдельным идемпотентным seed-файлом.

Тип проверки определяется схемой URL: `http://` или `https://`.

Альтернативы хранению статуса: память процесса (теряется), файл-снимок и compacted-топик (не атомарны
с `check_results`), Redis (лишний сервис ради 1000 строк).

### Порядок записи и отправки

Поток-писатель держит копию `site_state` в памяти и на каждый результат выполняет:

```text
1. compute new state (pure function, no I/O)
2. TX: INSERT check_results + UPDATE site_state
3. if is_up != notified_is_up:
     produce to Kafka, wait for ack
     UPDATE site_state SET notified_is_up = is_up
```

Падение до коммита не оставляет следов: следующая проверка определит статус заново. Падение после
коммита оставляет расхождение `is_up != notified_is_up`. Падение между подтверждением Kafka и отметкой
даёт дубль. Шаг 3 выполняется и при старте для всех расходящихся строк — до запуска планировщика.

Если Kafka не подтвердила отправку за таймаут, расхождение остаётся, и шаг 3 повторится на следующем
результате этого сайта. Отдельный цикл повторов не нужен.

Подтверждение ждём синхронно: смены статуса редки, а асинхронность потребовала бы отслеживать
незавершённые отправки.

Альтернатива «сначала Kafka, потом БД»: после падения БД не знает об отправленном «упал», и если сайт
успел восстановиться, сообщения о восстановлении не будет никогда. Полноценная таблица outbox лишняя:
на сайт достаточно одного незавершённого события, поэтому хватает колонки `notified_is_up`.

### Определение статуса

Чистая функция: на входе текущее состояние и результат, на выходе новое состояние. Падение — после
`FAILURES_TO_DOWN = 2` неудач подряд. Восстановление — первая успешная проверка. Значение порога
принято по умолчанию и меняется одной константой.

### Планировщик и пересчёт приоритета

Планировщик работает в главном потоке и раз в секунду перебирает сайты, сравнивая их `next_run`:
для 1000 сайтов это дёшево, а пересчёт интервалов не требует перестраивать кучу. У сайта есть
`std::atomic<bool> in_flight`: планировщик не ставит задачу, пока флаг поднят, а воркер снимает его
после `push` в очередь. Поэтому задач в пуле не больше числа сайтов, и backpressure доходит до
планировщика:

```text
writer slow --> queue full --> push blocks --> in_flight stays set --> site is skipped
```

Раз в 30 с планировщик читает из `check_results` число неудач за последние 15 минут по каждому сайту:
есть неудачи — интервал равен `max(10 c, base / 4)`, нет — `base`. Расчёт — чистая функция. Все данные
расписания принадлежат одному потоку, мьютекс не нужен.

Альтернативы: раунды с `std::latch` не поддерживают разные интервалы; таймер без `in_flight` накапливает
задачи в неограниченной очереди пула.

### Параметры пула и очереди

Число воркеров — `CHECKER_THREADS`, по умолчанию 32: воркеры ждут сеть, а не занимают CPU. При 1000 сайтах
и ответе 300 мс занято около 5 потоков; если не отвечает всё сразу, проверки становятся реже благодаря
`in_flight`. Ёмкость очереди равна числу сайтов.

### Очередь

`BoundedThreadSafeQueue` чинится вручную (определения в заголовке, поле `max_size_`, мьютекс во всех
методах, условные переменные `not_full_` и `not_empty_`) и получает `close()`. `push` и `wait_and_pop`
возвращают `bool`: после `close()` `push` возвращает `false`, а `wait_and_pop` отдаёт остаток
и возвращает `false`, когда очередь пуста.

### Kafka

- Клиент: librdkafka `v2.16.0` через FetchContent, C++ API, без SSL и SASL. FetchContent — как для остальных
  зависимостей; обёртки `cppkafka` и `modern-cpp-kafka` не дают здесь выгоды.
- Брокер: `apache/kafka:4.4.0` в режиме KRaft в `docker-compose.yml`, с томом для данных.
- Топик `site-status`, одна партиция, авто-создание брокером. Ключ — URL, значение — JSON
  (`url`, `is_up`, `http_code`, `changed_at`).
- Producer: `acks=all`, `enable.idempotence=true`. Consumer: группа `tgbot`,
  `enable.auto.commit=false`, `auto.offset.reset=earliest`.
- Код в `internal/kafka`; писатель и бот зависят от интерфейсов, тесты подменяют их фейками.
- Адрес брокера — `KAFKA_BROKERS`.

### Бот

Два потока, общий только флаг остановки:

- **Consumer**: читает событие, получает подписчиков из БД, отправляет каждому, коммитит offset
  только после обработки всех.
- **Poll**: `getUpdates`, разбор команд, запись подписок, ответ пользователю. Неразбираемый ответ Telegram
  пропускается, а не роняет процесс.

Разбор команд и классификация ответа Telegram — чистые функции. Отправка получает таймаут 10 с:

| Ответ Telegram | Действие |
|---|---|
| 200 | успех |
| сетевая ошибка, 429, 5xx | пауза (для 429 — `retry_after`), повтор того же сообщения |
| прочие 4xx | получатель пропускается, запись в лог |

Токен есть в URL запроса, поэтому URL и ошибки cpr в лог не пишем.

`/subscribe` работает как замена списка в одной транзакции: нужна только такая семантика, потому что
в требованиях пользователь передаёт список целиком.

### Чекеры

`HTTPSChecker` начинает ходить в сеть через `net::IFetcher`, как `HTTPChecker`: cpr одинаково работает
с обеими схемами. `Fetcher` без состояния, один на процесс, передаётся в `Builder::CreateChecker`
и живёт дольше пула. Чекеры создаются один раз на старте.

### Остановка

Обработчик SIGINT/SIGTERM взводит атомарный флаг, планировщик проверяет его не реже раза в секунду.

```text
stop scheduler --> ~ThreadPool (drain, join) --> queue.close()
               --> writer drains, exits --> join
```

В боте оба потока проверяют флаг между операциями. Если Docker завершит процесс раньше, данные
не пострадают: это обычный сценарий падения.

## Risks / Trade-offs

- [Дубль при падении между отправкой и фиксацией] → Принято: у `sendMessage` нет идемпотентности.
- [Синхронное ожидание Kafka задерживает писателя] → Смены статуса редки, ожидание ограничено таймаутом,
  очередь и `in_flight` гасят задержку.
- [Один брокер без реплик: потеря диска теряет события] → Том для данных; для учебного проекта приемлемо.
- [Сайт упал и поднялся, пока чекер не работал] → Не обнаруживается, истории проверок за это время нет.
- [Пока сайт в процессе подтверждения падения, он опрашивается по базовому интервалу до пересчёта]
  → Задержка не больше 30 с пересчёта, значения подбираются константами.
- [`check_results` растёт без ограничения] → Запрос по окну опирается на индекс `(url, checked_at DESC)`;
  очистка вне этого изменения.
- [Подписчик появился, когда сайт уже лежит] → Сообщения о падении не будет, придёт только
  о восстановлении; поведение соответствует требованию «только при смене статуса».
- [`PG::PGStore` и `Storage` становятся неиспользуемым кодом] → Оставлены намеренно, судьбу решить
  отдельно.

## Migration Plan

1. Поднять Postgres и Kafka через `docker compose`.
2. Применить `db_description.sql` и seed со списком сайтов.
3. Задать `KAFKA_BROKERS` и `CHECKER_THREADS` в окружении.
4. Запустить `DevOpsBot` и `TelegramBot`.

Откат: остановить процессы и вернуться на прежнюю ветку. Новые таблицы старый код не использует.
